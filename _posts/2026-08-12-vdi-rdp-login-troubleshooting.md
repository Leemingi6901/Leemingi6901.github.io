## 문제 상황

신규 Active Directory(`contoso.local`)를 구축하고, 신규 VDI에 사용자 계정을 생성한 뒤 RDP로 로그인을 시도했다. ID/PW를 입력하면 Windows 로그인 화면까지는 정상적으로 진행되지만, 그 직후 아래와 같은 오류가 발생했다.

```
원격으로 로그인하려면 원격 데스크톱 서비스를 통해 로그인할 수 있는 권한이 있어야 합니다.
```

인증(ID/PW) 자체는 통과했다는 점에서, 네트워크 연결이나 계정 자격 증명 문제가 아니라 **RDP 로그온 권한 문제**라는 걸 짐작할 수 있었다.

## 1차 원인: 원격 데스크톱 로그온 권한

Windows에서 RDP로 로그인하려면 대상 컴퓨터의 로컬 보안 정책(또는 GPO)에서 다음 두 가지를 만족해야 한다.

- **"원격 데스크톱 서비스를 통한 로그온 허용"** 목록에 계정(또는 소속 그룹)이 포함되어 있을 것
- **"원격 데스크톱 서비스를 통한 로그온 거부"** 목록에는 포함되어 있지 않을 것

기본적으로 이 권한은 `Administrators`와 `Remote Desktop Users` 로컬 그룹에게 부여되어 있다. 신규로 생성한 사용자 계정은 당연히 이 그룹에 속해 있지 않았기 때문에 발생한 문제로 추정하고 확인을 시작했다.

## 확인 과정에서 겪은 삽질들

### 1) 로컬 정책은 도메인 컨트롤러에서 확인할 수 없다

처음에 `lusrmgr.msc`를 열었더니 이런 오류가 떴다.

```
DC01 컴퓨터는 도메인 컨트롤러입니다.
이 스냅인은 도메인 컨트롤러에서 사용할 수 없습니다.
도메인 계정은 Active Directory 사용자 및 컴퓨터 스냅인으로 관리합니다.
```

도메인 컨트롤러(DC)에는 로컬 계정/로컬 그룹 개념 자체가 없다. 실수로 VDI 서버가 아니라 DC(`DC01`)에서 로컬 정책을 열려고 했던 것이 원인이었다. VDI 서버의 권한 문제는 VDI 서버 자체 또는 그 서버가 속한 OU에 연결된 **GPO**로 관리해야 한다.

### 2) GPO 우선순위와 OU 상속 구조 확인

그룹 정책 관리(GPMC)에서 확인해보니 `VDI` OU에는 두 개의 GPO가 연결되어 있었다.

| 우선순위 | GPO | 연결 위치 |
|---|---|---|
| 1 | Corp-VDI-GPO | 상위 OU(연구소)에서 상속 |
| 2 | Site-VDI-GPO | VDI OU에 직접 연결 |
| 3 | Default Domain Policy | 도메인 루트 |

두 GPO를 각각 열어 **컴퓨터 구성 → 정책 → Windows 설정 → 보안 설정 → 로컬 정책 → 사용자 권한 할당 → "원격 데스크톱 서비스를 통한 로그온 허용"** 항목을 확인했는데, 둘 다 **"정의되지 않음"** 상태였다. 즉 GPO에서 이 권한을 명시적으로 제한하고 있는 게 아니었고, 로컬 기본값(Administrators + Remote Desktop Users)이 그대로 유효한 상황이었다.

### 3) 컴퓨터 계정이 VDI OU에 없었다

여기서 진짜 원인을 발견했다. VDI가 AD 자체에서 생성된 게 아니라, **외부 VDI 플랫폼에서 만들어진 뒤 도메인 조인만 되는 구조**였다. 이런 경우 도메인 조인 시 OU를 별도로 지정하지 않으면 컴퓨터 계정이 기본 **Computers 컨테이너**에 생성되고, GPO가 걸려있는 `VDI` OU에는 들어가지 않는다.

해결책은 두 가지로 정리했다.

**당장 해당 서버만 수정:**
- ADUC의 Computers 컨테이너에서 대상 컴퓨터를 찾아 `VDI` OU로 드래그 앤 드롭 이동
- 이동 후 대상 서버에서 `gpupdate /force`

**앞으로 조인되는 VDI들에 자동 적용(근본 해결):**
```powershell
redircmp "OU=VDI,OU=연구소,OU=Contoso,DC=contoso,DC=local"
```
이 명령으로 기본 컴퓨터 조인 위치를 Computers 컨테이너 대신 VDI OU로 리다이렉트할 수 있다.

### 4) RDP 인증서 이름이 접속 주소와 다르게 뜨는 현상

`10.0.0.100:33389`로 접속했는데 인증서 이름이 `VDI-016`으로 표시되어 당황했다. 이건 오류가 아니라 정상 동작이다. RDP는 기본적으로 **자체 서명 인증서**를 쓰고, 이 인증서의 이름은 접속에 사용한 IP나 포트가 아니라 **실제 대상 컴퓨터의 호스트명**을 사용한다. 포트포워딩/브로커를 통해 접속하는 구조라면 이런 이름 불일치는 흔히 발생한다.

다만 이 과정에서 실제 접속되는 컴퓨터명(`VDI-016`)이 앞서 AD에서 확인했던 목록(`VDI-001`, `VDI-002`)과 다르다는 걸 알게 되어, 컴퓨터 계정 위치를 다시 점검하는 계기가 되었다.

### 5) 방화벽이 RDP 포트 하나만 열려 있었다

가장 답답했던 부분. 원격 관리(`compmgmt.msc` 원격 연결, PsExec, WinRM 등)로 문제를 해결하려 했지만, 방화벽 정책상 **RDP로 매핑된 포트(33389) 외에는 전부 차단**되어 있어 SMB/RPC/WinRM 기반의 원격 관리 도구를 전혀 쓸 수 없었다.

결국 남은 방법은 하나였다.

## 최종 해결

1. 문제가 되는 사용자 계정 대신, **도메인 관리자 계정**(`contoso\administrator`)으로 동일한 RDP 주소(`10.0.0.100:33389`)에 접속
   - 도메인 조인된 컴퓨터에서 Domain Admins 그룹은 기본적으로 로컬 Administrators 그룹에 포함되므로, 별도 권한 부여 없이도 로그인이 가능했다
2. 관리자 세션 안에서 `lusrmgr.msc` 실행
3. **그룹 → Remote Desktop Users** → 문제의 사용자 계정 추가
4. 확인용으로 관리자 권한 CMD에서
   ```
   net localgroup "Remote Desktop Users"
   ```
   실행하여 계정이 정상적으로 포함됐는지 확인
5. 관리자 세션 로그아웃 후, 해당 사용자 계정으로 재접속 → 정상 로그인 확인

## 정리 / 체크리스트

새 AD + 외부에서 프로비저닝되는 VDI 조합에서 RDP 로그인이 안 될 때 확인할 순서를 정리하면 다음과 같다.

- [ ] 오류가 "로그인 화면 이전"인지 "로그인 화면 이후"인지 구분 (인증 문제 vs 권한 문제)
- [ ] 로컬 정책 확인은 반드시 **대상 서버**에서 (DC에서는 불가)
- [ ] 해당 서버가 속한 OU에 연결된 GPO의 "원격 데스크톱 서비스를 통한 로그온 허용/거부" 정의 여부 확인 (우선순위 높은 GPO부터)
- [ ] 컴퓨터 계정이 실제로 의도한 OU(GPO가 걸린 OU)에 있는지 확인 — 특히 외부에서 조인만 하는 VDI라면 기본 Computers 컨테이너에 남아있을 가능성 높음
- [ ] 필요하면 `redircmp`로 기본 조인 위치를 원하는 OU로 리다이렉트
- [ ] RDP 인증서 이름 불일치는 정상 동작 — 오히려 실제 접속 대상 호스트명을 확인하는 단서로 활용
- [ ] 방화벽이 RDP 포트만 열려있는 폐쇄 환경이라면, 원격 관리 도구 대신 **이미 권한 있는 관리자 계정으로 RDP 접속 후 내부에서 직접 조치**하는 방법을 최우선 고려
- [ ] 근본 원인(권한 없는 그룹)을 고쳤으면, 향후 동일 문제 재발 방지를 위해 GPO 기본 설정(Preferences → 로컬 사용자 및 그룹)으로 자동화 고려
