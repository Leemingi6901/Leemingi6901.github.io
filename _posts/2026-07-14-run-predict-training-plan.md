안녕하세요, 멩기입니다.

개인 프로젝트로 만들고 있는 러닝 대회 예측 앱 **RUN Predict**에 오늘(2026.07.14) "목표 완주시간을 달성하기 위한 맞춤 훈련 계획" 기능을 새로 만들고, 만드는 과정에서 나온 버그들을 하나씩 고친 하루였습니다. 기능 하나를 붙였다가 이상한 점을 발견하고 → 원인 분석하고 → 다시 고치는 과정을 계속 반복했는데, 그 흐름을 정리해봅니다.

---

## 🏃 RUN Predict가 뭔가요?

체성분, 러닝 기록, 대회 코스/기후 정보를 바탕으로 **예상 완주시간과 컷오프 통과 여부**를 예측해주는 개인용 웹앱입니다. Next.js 16 + Prisma + SQLite로 만들었고, 예측 엔진은 Jack Daniels의 **VDOT(유산소 능력 지표)** 공식을 기반으로 합니다. 오늘 이전까지는 "예상 완주시간 예측 + what-if 시나리오(체중 감량, 기록 단축 시 얼마나 빨라지는지)" 까지 구현되어 있었고, 오늘은 여기에 "그래서 이 목표를 달성하려면 어떻게 훈련해야 하는데?"에 대한 답을 주는 기능을 추가했습니다.

---

## 1️⃣ 목표 완주시간 기반 훈련 계획 뼈대 만들기

먼저 대회별로 목표 완주시간을 입력할 수 있게 하고, 그 목표를 달성하는 데 필요한 VDOT을 역산했습니다. 그리고 대회일까지 남은 기간을 훈련 주기화 이론에 맞춰 **기초 → 빌드업 → 피크 → 테이퍼** 4단계로 나누고, 단계별로 주간 훈련량과 이지/템포/인터벌/롱런 페이스를 계산하도록 만들었습니다.

```ts
export function vdotForPhase(phase: TrainingPhase, currentVdot: number, targetVdot: number): number {
  if (targetVdot <= currentVdot) return currentVdot;
  return currentVdot + (targetVdot - currentVdot) * PHASE_GOAL_PROGRESS[phase];
}
```

여기까지 만들고 나서 요일별로 "화요일: 템포런 2km, 일요일: LSD 4km" 처럼 구체적인 세션까지 펼쳐 보여주는 UI도 붙였습니다.

---

## 2️⃣ 버그 #1 — LSD가 1.4km라고?

처음 만든 버전을 확인해보니 롱런(LSD) 훈련이 **1.4km**로 나오는 이상한 결과가 나왔습니다. 계산 자체는 맞았는데, 원인은 "최근 4주 평균 주간 거리"를 훈련량의 기준점으로 삼았기 때문이었습니다. 최근에 짧은 템포런만 몇 번 기록해뒀더니 주간 평균이 5km밖에 안 됐고, 그 28%를 롱런으로 배정하니 1.4km가 나온 거죠.

**해결**: 최근 로그는 "참고용" 정보로만 화면에 보여주고, 실제 훈련량 산정은 **검증된 VDOT(또는 목표 VDOT)**와 **대회 거리**를 기준으로 다시 짰습니다. 롱런도 "주간거리의 일정 비율"이 아니라 대회 거리 자체를 기준(풀코스 기준 약 83% ≈ 35km)으로 별도 산정하도록 분리했고요. 다만 1주차부터 피크의 절반(17.5km)으로 훅 뛰면 부상 위험이 크니, 시작점은 안전하게 10.5km로 낮추고 점진적으로 35km까지 올라가게 했습니다.

## 3️⃣ 버그 #2 — 페이스가 1주차나 15주차나 똑같다

목표 시간을 따로 안 세우면 페이스 표가 기초/빌드업/피크/테이퍼 전부 똑같이 나오는 문제도 있었습니다. 원인은 "목표가 없으면 그냥 현재 VDOT을 계속 쓴다"는 로직이었어요. 생각해보면 목표를 안 세워도 15주짜리 체계적인 훈련을 거치면 당연히 어느 정도는 빨라지는 게 정상이죠. 그래서 목표가 없을 땐 **훈련 사이클(12~16주) 동안 보수적으로 기대할 수 있는 VDOT +4% 향상**을 기본 목표로 가정하도록 바꿨습니다.

```ts
export const DEFAULT_FITNESS_GAIN = 1.04;

export function resolveTargetVdot(currentVdot: number, goalVdot: number | null): number {
  return Math.max(goalVdot ?? 0, currentVdot * DEFAULT_FITNESS_GAIN);
}
```

## 4️⃣ 버그 #3 — 요일 라벨이 실제 요일과 안 맞음

주차별 계획에 월/화/수/목/금/토/일로 요일을 표시했는데, 알고 보니 "오늘 날짜"를 무조건 1일차(월요일 자리)로 넣고 있어서 실제 요일과 라벨이 어긋나 있었습니다. 매주 시작을 **그 주의 월요일로 스냅**하도록 고쳤습니다.

```ts
function mondayOfWeek(d: Date): Date {
  const date = new Date(d);
  date.setHours(0, 0, 0, 0);
  const day = date.getDay(); // 0=일 ... 6=토
  const diffToMonday = day === 0 ? -6 : 1 - day;
  date.setDate(date.getDate() + diffToMonday);
  return date;
}
```

## 5️⃣ 페이스보다 심박존이 낫다는 피드백

"페이스보다 심박존(zone)이나 심박수에 맞추는 게 낫다"는 피드백을 받고, Daniels 훈련강도(E/M/T/I)에 흔히 대응되는 **%최대심박수 구간(Z1~Z5)** 을 페이스 옆에 같이 보여주도록 추가했습니다.

| 세션 | Zone | %HRmax |
|---|---|---|
| 리커버리 | Z1 | 55~65% |
| 이지런 / LSD | Z2 | 65~78% |
| 마라톤 페이스 | Z3 | 80~86% |
| 임계치(템포) | Z4 | 87~92% |
| 인터벌 | Z5 | 93~100% |

그리고 %만 보여주면 정확한 bpm을 알 수 없으니, **체성분 기록에 최대심박수 입력란**을 새로 추가했습니다. 최대심박수를 입력하면 훈련 계획 화면의 심박존이 자동으로 "Z4 · 158~167bpm" 처럼 실제 bpm 범위로 바뀌고, 안 넣으면 % 표기 + 입력 유도 문구가 뜹니다.

## 6️⃣ 자잘한 가독성 개선

- 요일별 세션 목록이 배지 텍스트 길이 때문에 줄마다 삐뚤빼뚤했던 걸 CSS Grid로 고정 컬럼 정렬
- 주차 카드마다 단계(기초/빌드업/피크/테이퍼)별 색상 왼쪽 테두리 추가해서 스크롤하면서 구간 구분이 바로 보이게 함
- 휴식일은 텍스트를 옅게 처리해서 실제 훈련일에 시선이 가도록 조정
- 요일별 목록에 헤더 행(요일/세션/내용/심박존/페이스) 추가

## 🛠️ 그 외 삽질 포인트

- Prisma 스키마를 두 번(목표시간 필드, 최대심박수 필드) 수정했는데, 매번 `npx prisma generate` 만으로는 부족하고 **Turbopack 개발서버가 이전 빌드를 캐시**하고 있어서 `.next` 폴더를 지우고 서버를 재시작해야 진짜 반영되는 걸 다시 한 번 확인했습니다.
- 브라우저 자동화로 폼 제출 테스트할 때 클릭이 씹히는 경우가 종종 있어서, `form.requestSubmit()`을 직접 호출해서 검증하는 방식으로 우회했습니다.

## ✅ 마무리

오늘은 기능 하나(맞춤 훈련 계획)를 만들면서 총 5개의 버그를 순서대로 발견하고 고쳤습니다:

1. 롱런이 비현실적으로 짧게 나오는 문제 → VDOT/목표 기반 볼륨 산정으로 재설계
2. 페이스가 전 구간 동일하게 나오는 문제 → 기본 체력향상치(+4%) 가정 추가
3. 요일 라벨이 실제 요일과 안 맞는 문제 → 월요일 스냅
4. 페이스만으론 부족하다는 피드백 → 심박존(Z1~Z5, %HRmax) 추가
5. 정확한 bpm이 필요하다는 요구 → 최대심박수 입력 기능 추가

작은 기능 하나도 실제로 써보면서 이상한 부분을 잡아나가야 진짜 쓸만해진다는 걸 다시 느낀 하루였습니다. 다음에는 실제 워치/앱 연동이나, 인터벌 세트 구성(반복 횟수·거리)을 좀 더 정교하게 다듬어볼 계획입니다.
