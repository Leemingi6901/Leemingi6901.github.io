안녕하세요, 멩기입니다.

[지난 글](/posts/daniel-work-tracker/)에서 소개한 업무 일지 대시보드 **Daniel Work Tracker** 후속편입니다. 10월 12일부터는 이 앱에 실제 업무를 적을 예정이라, 그 전에 "여기에 진짜 업무를 맡겨도 되나?"를 확인하는 작업을 했습니다.

이번에는 기능을 붙이지 않았습니다. 대신 이 세 가지를 했습니다.

- 장애가 나면 되살리는 길 만들기
- 시스템 점검과 알림 2주치 백테스트
- 저장소를 Vercel Blob에서 Neon(Postgres)으로 옮기기

---

## 1️⃣ Vercel이 끊겨도 되살릴 수 있게

기준은 "Vercel 구독이 끊겨도 GitHub에서 코드를 받아 로컬에서 바로 돌릴 수 있을 것"으로 잡았습니다.

- **백업:** GitHub Actions가 하루 두 번(00시·12시) 앱의 백업 API를 불러서, 같은 저장소의 `backups` 브랜치에 `snapshots/날짜.json`으로 커밋합니다.
- **복구:** 저장소에 로컬 파일 백엔드를 하나 더 만들어서, 명령 두 줄로 끝나게 했습니다.

```bash
npm run restore     # backups 브랜치의 최신 백업 → local-data/
npm run dev:local   # 로컬 파일 저장소로 앱 실행
```

같은 백업을 `--target postgres`로 넣으면 운영 DB도 되살릴 수 있습니다.

---

## 2️⃣ 점검 — 가장 큰 구멍은 요금제였습니다

무료 한도를 실제 사용량으로 계산해 보니 생각보다 심각했습니다. Vercel Blob 무료 플랜은 단건 조회가 **월 10,000회**이고, 넘으면 **30일 동안 막힙니다.**

그런데 정확성 문제 때문에 목록을 읽을 때 레코드마다 따로 조회하게 만들어 둔 상태였습니다.

- 업무 300건이면 대시보드를 한 번 열 때 조회가 **약 600회** 듭니다.
- 결국 한 달에 **화면을 20번도 못 엽니다.**
- 백업도 한 번에 목록 조회를 50회 넘게 써서, 하루 두 번이면 그것만으로 한 달 한도를 씁니다.

그래서 결론은 **입사 전에 Neon으로 옮기기**였습니다. 그 사이에도 버티도록 백업은 전체 경로를 한 번에 훑게 바꾸고, 캘린더 구독 피드는 CDN에 15분 캐시하게 했습니다.

점검에서는 이것들도 함께 잡았습니다.

- **알림 중복:** 09시에 tick 두 번이 동시에 오면 일보가 두 번 갈 수 있었습니다. "보냈나 확인 → 보내기"를 **"기록 선점 → 보내기"**로 바꿨습니다. Postgres는 `onConflictDoNothing`으로 같은 id가 이미 있으면 선점에 실패하게 했습니다.
- **주간 요약 재시도 누락:** 일보는 나가고 금요일 주간 요약만 실패하면 다시 보내지 않았습니다.
- **보내는 시간대:** 서버가 밤에 깨어나도 일보를 밤에 보내지 않도록 시간대를 정했습니다.
- **빈 백업:** 저장소 오류로 0건이 오면 최신 백업을 빈 파일로 덮지 않도록 막았습니다.
- **시간대 버그:** UTC로 도는 서버에서 KST 09시 전에는 "오늘"이 어제로 계산되던 곳을 고쳤습니다.
- **로그인 보강:** 상수 시간 비교, 실패 지연, iframe 차단을 넣었습니다.

## 3️⃣ 알림 2주치 백테스트

단위 테스트는 "이 시각에 무엇을 보낼 계획인가"만 확인합니다. 실제로는 tick이 계속 들어오고, 그 사이에 서버가 멈추고, 텔레그램이 실패하기도 합니다.

그래서 가짜 텔레그램을 붙여 **2주를 5분마다** 돌리는 시뮬레이션을 만들었습니다. 일부러 섞은 상황은 이렇습니다.

- 매일 09시 tick 동시 2회
- 아침 서버 멈춤(11시 복구 / 오후까지 멈춤)
- 텔레그램 502 오류
- 토큰 누락
- 반복 업무를 체크한 날과 안 한 날
- 회의를 늦게 등록

끝에서 "모든 알림은 딱 한 번", "텔레그램에 간 글 수 = 기록 수", "보낸 시각은 07~22시"를 확인하는데, 21건이 전부 기대대로 나갔습니다.

재밌었던 건 처음에 실패한 두 번이 코드가 아니라 **제 기대값**이 틀린 경우였다는 점입니다. 시뮬레이션은 제가 머릿속에 그린 동작까지 검증해 주더라고요.

## 4️⃣ Neon 전환 — 비밀값을 PC에 두지 않고

원래 계획은 `vercel env pull`로 DB 주소를 받아서 이 PC에서 이관 스크립트를 돌리는 것이었습니다. 그런데 받아 보니 값이 전부 `"[sensitive]"`였습니다. Neon 연동 변수는 잠겨 있어서 내려받을 수 없더라고요. 게다가 회사 PC라 DB 열쇠를 남기는 것도 좋지 않았습니다.

그래서 이관을 **Vercel 빌드 안에서** 하게 바꿨습니다.

```json
"build": "tsx scripts/db-migrate.ts && next build"
```

- `DATA_STORE=postgres`면 빌드 때 표를 만들거나 최신으로 맞춥니다.
- `MIGRATE_FROM_BLOB=1`이면 Blob 데이터를 Neon에 복사하고 원본과 대조합니다. 하나라도 다르면 빌드를 멈추니, 앱은 이전 배포로 안전하게 계속 돕니다.
- 테스트 데이터 15건이 모두 일치하는 걸 빌드 로그로 확인했습니다.
- 그다음 1회용 스위치는 바로 껐습니다. 남겨 두면 나중에 지운 데이터가 다음 배포 때 Blob에서 되살아나기 때문입니다.

---

## 5️⃣ GitHub 자동 백업 살리기

백업 워크플로는 계속 401로 실패하고 있었습니다. GitHub에 넣은 키(`CRON_SECRET`)가 Vercel 값과 달랐던 건데, Vercel 쪽 값은 민감 정보라 다시 볼 수도 없었습니다.

그래서 새 키를 만들어 화면에 띄우지 않고 클립보드로만 옮겨 양쪽에 넣었습니다.

```powershell
([guid]::NewGuid().ToString('N') + [guid]::NewGuid().ToString('N')) | Set-Clipboard
```

재배포한 뒤 워크플로를 돌리니 `backups` 브랜치에 `backup 2026-10-01 13:39 KST (15건)`이 쌓였습니다. 백업 파일 안의 `"store": "postgres"`로 운영이 Neon에서 읽고 있다는 것도 확인했습니다.

---

## 6️⃣ 마무리

이번에 배운 건 두 가지입니다.

1. **무료 한도는 설계 조건입니다.** 정확성을 위해 넣은 조회 한 번이 레코드 수만큼 곱해지니, 한 달 한도가 화면 20번이 됐습니다.
2. **장애 상황은 시뮬레이션으로 돌려 봐야 보입니다.** 동시 요청, 실패 후 재시도, 서버 멈춤을 섞어 보니 혼자 읽어서는 못 찾은 구멍이 나왔습니다.

남은 고도화는 백업이 Vercel을 거치지 않고 GitHub에서 Neon으로 바로 가게 하는 것입니다.
